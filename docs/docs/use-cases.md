# Варіанти використання v1.0

[← Назад: Модель UML](../model/README.md) | [Далі: Activity UC-03 →](activity-UC-03.md)

![Use Case Diagram v1.0](images/use-case.png)

Менеджер веде клієнтів і автомобілі, оформлює замовлення та керує їхнім статусом; Майстер виконує призначені роботи; Керівник переглядає поточні й завершені замовлення, а також дані клієнтів і автомобілів. Менеджер також веде облік деталей, потрібних для робіт, а Клієнт відстежує стан свого замовлення і деталей — лише перегляд, без облікового запису.
Відношення «include» показують обов’язкові частини сценаріїв: оформлення замовлення завжди починається з пошуку й перегляду автомобіля (UC-11); виконуючи роботу, майстер звіряється з обліком її деталей (UC-09); виконання призначеної роботи включає перевірку умови зміни статусу замовлення (UC-04) — коли всі роботи виконано, замовлення позначається для переведення в «Готове до видачі»; облік деталей завжди включає перегляд стану замовлення і деталей (UC-10) — того самого подання, яке бачить Клієнт. Відношення «extend» показують умовні розширення: якщо автомобіль не знайдено, під час оформлення замовлення виконується UC-02; якщо не знайдено клієнта, під час додавання автомобіля — UC-01. Вимога FR-01 (вхід за роллю) є наскрізною і входить до передумов усіх варіантів використання працівників, тому окремим Use Case не моделюється; UC-10 виконується без входу. Діаграма не описує порядок перевірок і переходи станів — для цього використовуються специфікації, Activity Diagram і State Machine Diagram.

## UC-03 «Оформити замовлення»

Виконавець: Антропов Володимир. Activity Diagram: [activity-UC-03.md](activity-UC-03.md).

| Поле | Опис |
| --- | --- |
| **ID і назва** | UC-03 «Оформити замовлення» |
| **Мета** | Зафіксувати в системі замовлення для автомобіля клієнта з переліком тюнінгових робіт і відповідальними майстрами. |
| **Основний актор** | Менеджер |
| **Тригер** | Клієнт звернувся до ательє з автомобілем, і з ним погоджено перелік робіт. |
| **Передумови** | Менеджер увійшов у систему (FR-01); у системі є щонайменше один працівник із роллю «Майстер». |
| **Основний сценарій** | 1. Менеджер шукає автомобіль за держномером або VIN (UC-11).<br>2. Система показує знайдений автомобіль і дані власника.<br>3. Менеджер ініціює створення замовлення.<br>4. Система перевіряє, що для автомобіля немає активного замовлення.<br>5. Менеджер вводить опис побажань клієнта.<br>6. Менеджер додає роботу: вид, опис, орієнтовну вартість.<br>7. Система перевіряє дані роботи й додає її до переліку зі статусом «Заплановано».<br>8. Менеджер обирає для роботи відповідального майстра.<br>9. Кроки 6–8 повторюються для кожної погодженої роботи.<br>10. Менеджер підтверджує збереження замовлення.<br>11. Система зберігає замовлення з унікальним номером, датою створення і статусом «Нове» та додає перший запис до історії статусів.<br>12. Система показує картку замовлення з роботами, майстрами й сумою орієнтовної вартості. |
| **Альтернативні та виняткові потоки** | A1. Крок 2: автомобіль не знайдено — менеджер реєструє його (UC-02, а якщо немає клієнта — UC-01) і продовжує з кроку 3.<br>A2. Крок 4: для автомобіля вже є активне замовлення — система не створює нове й показує номер активного; сценарій завершується без змін.<br>A3. Крок 7: дані роботи некоректні (не обрано вид, порожній опис, вартість < 0) — система не додає роботу, позначає поля з помилками; повернення до кроку 6.<br>A4. Крок 8: майстра не обрано — робота залишається без майстра, система попереджає, що замовлення не можна буде передати в роботу, доки майстрів не призначено (FR-09). |
| **Постумови** | Успіх: замовлення у статусі «Нове» щонайменше з однією роботою збережене, в історії статусів є перший запис, замовлення відображається у списку поточних. Невдача (A2): нове замовлення не створено, дані не змінено. |
| **Пов’язані вимоги** | FR-06, FR-07, FR-08, FR-18; NFR-03, NFR-04 |
| **Критерії приймання** | AC-06, AC-07, AC-08, AC-22, AC-23 |

## UC-04 «Змінити статус замовлення»

Виконавець: Курицький Орест. Activity Diagram: [activity-UC-04.md](activity-UC-04.md).

| Поле | Опис |
| --- | --- |
| **ID і назва** | UC-04 «Змінити статус замовлення» |
| **Мета** | Перевести замовлення в наступний стан життєвого циклу відповідно до фактичного стану робіт і зберегти історію змін. |
| **Основний актор** | Менеджер |
| **Тригер** | Змінився фактичний стан замовлення: автомобіль передають майстрам, роботи завершено (замовлення позначене «усі роботи виконано» в UC-05), клієнт забирає автомобіль або відмовився від замовлення. |
| **Передумови** | Менеджер увійшов у систему; замовлення існує. |
| **Основний сценарій** | 1. Менеджер відкриває картку замовлення зі списку поточних (UC-06) або завершених (UC-07).<br>2. Система показує поточний статус і дії, дозволені для нього State Machine Diagram замовлення.<br>3. Менеджер обирає дію: «Передати в роботу», «Позначити готовим» або «Видати автомобіль».<br>4. Система перевіряє умову переходу: для «Передати в роботу» — усім роботам призначено майстра; для «Позначити готовим» — усі роботи мають статус «Виконано»; для «Видати автомобіль» — фіксує дату видачі.<br>5. Система встановлює новий статус: «В роботі», «Готове до видачі» або «Видане».<br>6. Система додає запис до історії статусів: попередній і новий статус, дата й час, користувач.<br>7. Система показує оновлену картку замовлення. |
| **Альтернативні та виняткові потоки** | A1. Крок 2: замовлення у фінальному статусі («Видане» або «Скасоване») — дозволених дій немає, картка відкривається лише для перегляду; сценарій завершується.<br>A2. Крок 3: менеджер обирає «Скасувати» (доступно для «Нове» та «В роботі») — система вимагає причину; без причини скасування не виконується; після введення причини система встановлює статус «Скасоване», зберігає причину і переходить до кроку 6.<br>A3. Крок 4: умову переходу не виконано — статус не змінюється, система показує роботи без майстра або невиконані роботи; історія не змінюється, сценарій завершується. |
| **Постумови** | Успіх: статус змінено лише переходом, дозволеним State Machine Diagram, до історії додано рівно один запис. Невдача: статус та історія замовлення не змінені. |
| **Пов’язані вимоги** | FR-09, FR-12, FR-13, FR-14, FR-15 |
| **Критерії приймання** | AC-09, AC-12, AC-13, AC-14, AC-15 |

## UC-05 «Виконати призначену роботу»

Виконавець: Таценко Андрій. Activity Diagram: [activity-UC-05.md](activity-UC-05.md).

| Поле | Опис |
| --- | --- |
| **ID і назва** | UC-05 «Виконати призначену роботу» |
| **Мета** | Відобразити в системі фактичний хід виконання роботи, щоб менеджер і керівник бачили актуальний стан замовлення. |
| **Основний актор** | Майстер |
| **Тригер** | Майстер розпочинає або завершує призначену йому роботу над автомобілем. |
| **Передумови** | Майстер увійшов у систему; йому призначено роботу в замовленні зі статусом «В роботі». |
| **Основний сценарій** | 1. Майстер відкриває перелік призначених йому робіт.<br>2. Система показує роботи майстра із замовлень «В роботі»: номер замовлення, автомобіль, вид і опис роботи, поточний статус.<br>3. Майстер обирає роботу; система показує облік її деталей (UC-09): назву, кількість і стан «Очікується» або «Отримано» — лише для перегляду.<br>4. Майстер обирає дію зміни статусу роботи.<br>5. Система перевіряє, що робота призначена цьому майстру, а замовлення досі має статус «В роботі».<br>6. Система визначає наступний статус роботи: «Заплановано» → «Виконується» або «Виконується» → «Виконано».<br>7. Система зберігає новий статус роботи з датою й часом зміни.<br>8. Система оновлює прогрес замовлення «виконано X з Y» у картці замовлення та в переліку майстра.<br>9. Система перевіряє умову зміни статусу замовлення (UC-04): якщо всі роботи замовлення виконано, позначає його у списку поточних як «усі роботи виконано», щоб менеджер перевів його в «Готове до видачі»; інакше статус замовлення не змінюється. |
| **Альтернативні та виняткові потоки** | A1. Крок 2: призначених робіт немає — система показує порожній перелік; сценарій завершується.<br>A2. Крок 5: робота не призначена цьому майстру або замовлення вже не «В роботі» (наприклад, скасоване) — система відхиляє зміну й пояснює причину; статус роботи не змінюється.<br>A3. Крок 6: робота вже «Виконано» — зміна статусу недоступна (повернення назад у v1.0 не передбачено); сценарій завершується без змін. |
| **Постумови** | Успіх: статус роботи змінено на наступний, час зміни збережено, прогрес замовлення актуальний; якщо виконано всі роботи, замовлення позначене для зміни статусу (UC-04). Невдача: стан роботи й замовлення не змінено. |
| **Пов’язані вимоги** | FR-10, FR-11, FR-19 |
| **Критерії приймання** | AC-10, AC-11, AC-19 |
